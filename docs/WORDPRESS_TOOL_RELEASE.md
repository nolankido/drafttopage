# Markdown to WordPress acquisition tool

## User outcome

The public /markdown-to-wordpress/ route gives visitors with an existing article a direct, free workflow: paste simple Markdown, read the live preview, inspect local handoff findings, approve, and take editable WordPress blocks or the six-file kit. No account, plugin, or AI activation is required. The route uses the same editor, bounded validation, backup, revisions, approval, and export controllers as /write/. Its reading preview starts open; notes and other editing tools remain available.

The page has a descriptive title, unique description, self-canonical URL, sitemap entry, current navigation item, and homepage draft/sample links. An original guide explains the complete manual workflow, supported subset, limits, clipboard fallback, file import, and data handling. Its fictional input/output example is generated by the actual converter and rendered as escaped text. These changes make a focused entry page available for search and sharing. Search indexing, ranking, traffic, acquisition, and retention are unmeasured; no growth result is claimed.

The data-use page now states that WordPress kits include article-derived local handoff findings. Private source notes, private review questions, authentication, and checkpoint history remain excluded from the kit. Drafts still stay in tab memory until an explicit copy or download, with no autosave or automatic publishing.

## Validation and release

- 211 Node tests pass, including identical shared control IDs, unique metadata, canonical and sitemap inclusion, generated-example correctness, inert markup, documented limits, and accurate export disclosures.
- Static checks pass across 23 HTML pages: links, anchors, accessible references, asset/module loading, protected routing, syntax, privacy guards, and absent GitHub Actions workflows. Whitespace checks and Python browser-fixture compilation pass.
- The browser fixture adds sample loading, live preview, source findings, approved exact-body ZIP contents, edit resets, and 1440/390/320 layouts on the acquisition route. Execution is blocked by the missing Chromium executable. The mobile fixture is unexecuted; responsive CSS alone is not proof of mobile behavior. Live desktop validation and the native Cloudflare deployment result are recorded in the PR after release.
- The normal /write/ workflow remains available. Conversion code and block serialization are unchanged. WordPress themes, plugins, and versions still require the author to inspect the actual destination.

Deploy through the existing native Cloudflare Git integration after a feature-branch PR. No GitHub Actions workflow, cron, tracking, third-party request, new account, paid service, or persistent draft store is added or enabled.
